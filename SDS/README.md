# SDS 헌법

SDS(Shin Development System)는 단순한 문서 폴더가 아니다.  
누가 개발하더라도 같은 방식으로 회사와 제품을 이해하고 일하게 만드는 개발 운영체제(Development Operating System)다.

새 프로젝트를 시작할 때 이 폴더를 복사하면, 코드뿐 아니라 회사의 일하는 방식도 함께 시작된다.

SDS의 목적은 AI가 코드를 작성하도록 만드는 것이 아니라, 좋은 의사결정을 반복 가능하게 만드는 것이다.

## 역할의 경계

### SDS = 회사 운영 시스템

프로젝트가 달라져도 재사용할 수 있는 내용을 둔다.

- 개발 방식과 원칙
- AI 팀의 역할과 협업 방식
- 의사결정 기준과 기록 방식
- 프로젝트 관리와 출시 프로세스
- 자동화 규칙과 재사용 템플릿

### docs = 프로젝트 문서

현재 제품에만 필요한 사실과 산출물을 둔다.

- 제품별 API·인프라·데이터베이스 문서
- UI·디자인·기능 명세
- 리서치와 회의 기록
- 버그, 릴리즈 노트, 운영 이력

현재 프로젝트의 브랜드, 기능, 화면, 기술 선택을 SDS에 복사하지 않는다.  
그 내용은 `docs/`에 남긴다.

## 새 문서를 둘 곳

새 문서를 만들기 전 먼저 다음을 판단한다.

1. 다른 프로젝트에서도 그대로 쓸 수 있는가?
2. 제품의 사실이 아니라 회사의 일하는 방법인가?

둘 다 그렇다면 `SDS/`에 둔다. 하나라도 아니라면 `docs/`에 둔다.  
애매하면 문서를 만들기 전에 두 위치와 이유를 먼저 제안한다.

## Golden Rules

아래 원칙은 제품과 프로젝트가 바뀌어도 유지한다.

1. 제품을 먼저 생각하고 코드를 작성한다.
2. 기능보다 사용자의 행동을 먼저 설계한다.
3. AI는 개발자가 아니라 팀원이다.
4. 같은 실수는 시스템으로 해결한다.
5. 자동화는 프로세스가 완성된 후 적용한다.

## 운영 계층과 읽는 순서

SDS는 다음 계층으로 움직인다.

```text
CEO
  ↓
SDS Brain
  ↓
Workflow
  ↓
AI Team
  ↓
Management
  ↓
Automation
  ↓
Project
```

기능을 검토하거나 코드를 작성하기 전에는 아래 순서로 필요한 문서를 읽는다.

1. `00_BRAIN/` — 회사의 기준과 이미 내려진 결정
2. `01_WORKFLOW/` — 이번 작업에 적용할 절차
3. `00_BRAIN/DECISIONS.md` — 작업과 관련된 결정 근거
4. `07_MEMORY/` — 관련 증거 규칙, 패턴, 교훈, Anti Pattern
5. `02_AI_TEAM/` — 맡은 역할의 책임과 검토 범위
6. 프로젝트의 `docs/`와 코드 — 제품의 현재 사실

모든 작업이 같은 절차를 밟지는 않는다. 변경 위험도에 따라 Workflow가 경량·표준·중대 절차를 정한다.

## SDS 자체의 상태

- 현재 버전: [`VERSION.md`](VERSION.md)
- 구현된 변경: [`CHANGELOG.md`](CHANGELOG.md)
- 예정된 발전: [`ROADMAP.md`](ROADMAP.md)

SDS의 버전과 상태는 구현·검증된 현재 사실만 기록한다.

## 구조

```text
SDS/
├── 00_BRAIN/        회사의 기준, 방향, 의사결정
├── 01_WORKFLOW/     일을 수행하는 표준 절차
├── 02_AI_TEAM/      AI 역할과 업무 범위
├── 03_MANAGEMENT/   현황, 할 일, 로드맵 운영 방식
├── 04_AUTOMATION/   검증된 작업의 자동화
├── 05_TEMPLATES/    프로젝트에서 재사용할 서식
├── 06_LOGS/         짧은 작업 일지와 관찰 기록
├── 07_MEMORY/       증거 기반 패턴, 교훈, Anti Pattern
└── 08_GOVERNANCE/   AI와 사람이 지켜야 할 변경·문서·버전 정책
```

SDS는 살아 있는 운영체제다. 반복되는 판단과 실수는 문서·템플릿·자동화로 옮겨 시스템을 더 단단하게 만든다.
